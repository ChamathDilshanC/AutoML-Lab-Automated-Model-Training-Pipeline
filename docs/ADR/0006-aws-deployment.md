# ADR 0006 — Deployment on AWS: App Runner, Fargate, RDS PostgreSQL and OIDC

- **Status:** Accepted (implemented in M8). **Partly superseded by [ADR 0007](0007-lambda-api-and-amplify-frontend.md):** the API now runs on Lambda instead of App Runner (closed to new customers), gets its secrets as Lambda environment variables, and the frontend can run on Amplify Hosting. The rest stands. The base layer has since been applied to one account; compute has not: see "What is verified".
- **Date:** 2026-10-24

## Context
M8 puts the system online: the frontend on Vercel, the API and the worker on AWS, a managed PostgreSQL database, and a deployment pipeline. The owner's budget is about 10 USD a month and the target is the AWS Free Tier where the account is eligible. Free Tier eligibility, limits and prices change and depend on the account, so nothing in this repository promises a cost of zero.

## Decisions

### 1. Where things run
| Part | Runs on | Why |
|---|---|---|
| Frontend | Vercel | Set up in the Vercel dashboard, not in Terraform; it only needs the API's URL |
| API (FastAPI) | AWS App Runner, from the ECR image | Public HTTPS and rollouts with no load balancer to pay for; ECS Fargate was the alternative and would need an Application Load Balancer for a public URL |
| Worker | ECS Fargate (one task, no inbound traffic), same image, command `worker` | Training outlasts what a request-driven service is designed for |
| Metadata | RDS PostgreSQL `db.t4g.micro`, single AZ, 20 GiB gp3, private subnets | The brief's choice |
| Files and queue | S3 and SQS from M6 | Unchanged ([ADR 0005](0005-s3-storage-and-sqs-job-queue.md)) |

### 2. One image, chosen by its first argument
`backend/Dockerfile` builds one image. `backend/docker/entrypoint.sh` runs `api` (default; applies migrations, then uvicorn), `worker`, `migrate`, or `cli ...`; anything else is executed as given. Only the production dependencies are installed, the process runs as an unprivileged user, and no secret is baked in.

### 3. PostgreSQL in production, SQLite only locally
`ENVIRONMENT=local` may use SQLite (still the default for development and the test suite). Any other environment refuses to start on SQLite. The connection is either a `DATABASE_URL` or its parts (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSLMODE`), which lets a platform inject the password as a separate secret; the password is URL-encoded by SQLAlchemy, never string-concatenated.

Outside `local` the application no longer creates tables itself. **Alembic** migrations (`backend/migrations`) are the schema's source of truth: the API container runs them on start (`python -m app.migrate`), under a PostgreSQL advisory lock so two starting containers cannot race, and a test fails if the models and the migration drift apart. The worker waits (up to `MIGRATION_WAIT_SECONDS`) for the schema to reach the head revision instead of crashing when it starts first.

### 4. Network without a NAT gateway
A NAT gateway is billed for every hour it exists, so the design avoids it.
- The **worker** runs in public subnets with a public IP so it can reach ECR, SQS and S3. Its security group has no inbound rule and allows only HTTPS and PostgreSQL out.
- The **database** and the API's **App Runner VPC connector** are in private subnets with no route to the internet. The API reaches S3 through a gateway endpoint and SQS through an interface endpoint (in one availability zone, to limit the hourly charge).
- The database accepts connections only from the API and worker security groups. It is not publicly accessible, is encrypted, and requires TLS (`rds.force_ssl`, `sslmode=require`).

### 5. Secrets: generated by Terraform, held in SSM, passed by reference
The database password and the token-signing key are generated with `random_password` and stored as SSM SecureString parameters. App Runner and ECS read them when a container starts, using the runtime's own role; they never appear in a task definition or service configuration as plain values.

This puts both values **in the Terraform state**, so the state must be kept private and encrypted (a remote backend with encryption and restricted access). RDS's managed master password was considered and not used: Secrets Manager rotates it on a schedule, and a container that was handed the old value in an environment variable would fail to sign in to the database until restarted. Making the application re-read a secret on each connection would also require a Secrets Manager endpoint in the private network. To rotate the password: `terraform apply -replace=random_password.db` then redeploy.

### 6. Deployment role: GitHub OIDC, no stored keys
`.github/workflows/deploy.yml` assumes an IAM role using GitHub's OIDC token. The role's trust policy requires the audience `sts.amazonaws.com` and an exact subject `repo:<owner>/<name>:environment:production`, so only jobs of this repository that run in the `production` GitHub environment can assume it (add required reviewers to that environment to gate deployments by hand). The role may log in to ECR, push to one repository, start an App Runner deployment and update one ECS service. It cannot create or change infrastructure, and cannot pass roles. Terraform itself is **not** run by the pipeline: infrastructure changes are applied by a person.

The workflow does nothing until the repository variable `DEPLOY_ENABLED` is `true`, so merging it cannot trigger a deploy into an account that is not set up.

### 7. Compute is opt-in and the worker starts stopped
`enable_compute` (default `false`) creates the App Runner and ECS services. It is false at first because both need an image that does not exist until the first push. `worker_desired_count` defaults to `0`: until it is set to `1`, experiments stay `QUEUED`. A running Fargate task bills for as long as it runs, so an always-on worker is the most likely reason for the budget to be exceeded.

### 8. Budget alert, not a cap
`aws_budgets_budget` emails at 80 % and 100 % of actual spend and at 100 % of forecast against 10 USD a month for the **whole account**. AWS Budgets never stops anything. When an alert arrives, stop the worker (`worker_desired_count = 0`) and, if needed, the API.

### 9. The real client address behind App Runner
The sign-in rate limiter keys on the client address. Behind a proxy the TCP peer is the proxy, so the application reads `X-Forwarded-For` only when told how many trusted proxies there are (`TRUSTED_PROXY_HOPS`, default 0 = ignore the header). It takes the entry that many positions from the **right**, the one the trusted proxy itself appended, because anything to its left was supplied by the client and can be forged. Terraform sets 1 for App Runner. That App Runner appends exactly one entry this way is an assumption to confirm on the first deployment (send a request with a forged `X-Forwarded-For` and check that the limiter still tracks the real address).

## Consequences
- The two services have a cost that is not covered by the Free Tier in every account: the SQS interface endpoint, the running App Runner instance and the running Fargate task are billed by the hour. Left running, the stack is likely to exceed 10 USD a month. See [DEPLOYMENT.md](../DEPLOYMENT.md) § "Cost and how to stop it".
- The tag `latest` moves with every deploy. The image tagged with the commit SHA is always pushed as well, so a rollback is re-tagging that image as `latest` and starting a deployment.
- Single-AZ database and single worker: no high availability. This is a portfolio deployment.

## What is verified
- The whole suite passes against a real PostgreSQL 18 as well as SQLite; migrations match the models exactly and upgrade, downgrade and run concurrently without error.
- A production-mode run on a real PostgreSQL through `entrypoint.sh` (worker started before the schema exists, API migrating then serving, sign-in, upload, training in a separate worker process, prediction, cascade delete, restart): 20 of 20 checks.
- `terraform fmt -check` and `terraform validate` pass against the real AWS provider; static tests of the security properties (checked by deliberately breaking each one); `actionlint` passes on every workflow.

## What is not verified
- `terraform apply`, and every AWS behaviour it creates: App Runner reaching RDS, SQS and S3 through the VPC connector and endpoints; secrets resolving; the Fargate worker starting; the OIDC trust; the budget emails.
- The Docker image has not been built on the author's machine (Docker was not running); it is built and started in CI.
- The `X-Forwarded-For` assumption above.
- The Vercel setup.
